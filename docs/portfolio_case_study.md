# Vivo Energy 360 — case study

> **Independent synthetic portfolio project.** No internal Vivo Energy, Engen,
> Shell or Vitol data. Every site, customer, employee, asset, coordinate,
> price, volume and incident is generated by the code in this repository.
> Company and person names are invented; any resemblance to a real
> organisation or individual is coincidental. Site coordinates are town
> centroids plus random jitter and do not represent any real service station.

---

## The brief

Build a data platform for a downstream energy business: a retail forecourt
network, a commercial B2B book, primary distribution, LPG, lubricants,
aviation, marine, loyalty and digital channels, EV and solar, asset
maintenance, safety, and finance. Model it on South Africa. Make it real
enough that the decisions taken on it would be defensible.

The additional constraint I set myself: **the data has to be dirty**. A
platform demonstrated on clean data demonstrates almost nothing, because the
difficult part of data engineering is not the join.

## 1. The data had to be worth modelling on

Random numbers are not a dataset. If transaction timestamps are uniform, a
demand forecast has nothing to learn and any model trained on it produces a
meaningless accuracy figure that nobody can interpret.

So the generator encodes the actual rhythms of the business:

- **Hour of day** — morning and evening commute peaks, dead between 02:00
  and 04:00.
- **Day of week** — Friday heaviest, Sunday lightest.
- **Season** — December holiday travel; LPG demand rises through winter.
- **Public holidays** — the day *before* a public holiday is the strongest
  fuel day of the year.
- **Regulated prices** — South African pump prices move in monthly steps, not
  as per-transaction noise, because they are set by regulation.
- **Site heterogeneity** — a `demand_index` per site combining urban class,
  national-route position, offer mix and a lognormal idiosyncrasy, so a
  Gauteng truck stop and a rural single-product site behave differently.
- **Asset condition** — older and more critical assets carry a higher failure
  propensity, which drives both how often they generate work orders and how
  likely each one is to be an unplanned breakdown.

That last point took two attempts. The first version weighted *which* assets
generated work orders but drew the maintenance type independently, so the
breakdown rate came out flat across asset age — 12%, 16%, 12%, 11% — and the
predictive-maintenance model had nothing to find. After making breakdown
probability depend on the asset's own condition, the rate rises 23% → 39% →
51% → 59% across age bands. Same row count; the difference is whether the
dataset means anything.

## 2. Then it had to be broken

Sixty-three million defects, modelled on the specific systems being
simulated rather than sprinkled at random:

| Source | Defect |
|---|---|
| Forecourt / shop POS | numbers as text: `"1 234,56"`, `"481,200"` |
| ERP extracts | `" s000123 "` — whitespace and casing that break joins silently |
| Any system | `"NULL"`, `"N/A"`, `"-"`, `""` standing in for a real null |
| Replayed batches | the same business key arriving twice, byte-identical |
| Telemetry | dropouts, stuck `-999` readings |
| Clock skew | timestamps at 1970-01-01 and 2099-12-31 |
| Manual entry | kilolitres typed into a litres field — exactly 1000× out |
| Integration drift | a `site_id` in the fact that the dimension has not received |
| Charset mismatch | `Gqeberha` → `GqeberhaÂ` |
| Finance | an amount in USD sitting in a column declared as ZAR |

Every defect is counted as it is injected and written to the build manifest.
That is the design decision that matters: it converts cleansing from a claim
into a measurement.

## 3. The cleansing has to account for everything

The cleansing layer runs in three generated stages: 167 `cln_` models repair
every column and assess every row, 167 `stg_` models take the valid rows and
deduplicate them, and 122 `qtn_` models keep every rejected row alongside the
rule that rejected it.

The reconciliation that has to hold:

```
raw rows = cleansed + quarantined + duplicates removed
```

A row that is neither cleaned nor rejected nor identified as a duplicate has
been silently lost, and a silently lost row becomes an unexplainable variance
three months later that nobody can trace. `obs_cleansing_summary` asserts this
for every monitored feed, and it is the first test in the integration suite.

The hardest single rule was numeric parsing. A comma is ambiguous: in
`"1,234.56"` it is a thousands separator, in `"1234,56"` it is the decimal
mark. Getting this wrong does not throw an error — it produces a number that
is wrong by three orders of magnitude and looks entirely plausible. The rule
is positional, documented in `macros/cleansing.sql`, and applied identically
in all 167 models, because the same value parsed two different ways in two
tables is worse than not parsing it at all.

Rejected rows are quarantined, never dropped. `obs_quarantine_reasons` breaks
rejections down by rule, because the operational response differs completely:
2,000 rows rejected for a missing `site_id` means an upstream join is broken
and someone must fix the source; 2,000 rejected for a negative amount is
usually legitimate credit notes arriving on the wrong feed.

## 4. The platform found two defects in itself

Both were caught by its own controls, which is the entire reason for having
them.

**A macro that silently corrupted every ratio.** `safe_divide('a - b', 'c')`
compiled to `a - (b / c)` because the macro did not parenthesise its
arguments. Every margin percentage, utilisation rate and share-of-total in the
project was wrong — and not obviously wrong, just quietly incorrect. It was
caught by a plausibility test asserting that `dim_product.base_margin_pct`
falls between −5 and 100. A `not_null` test would never have found it.

**A general ledger that did not balance.** The generator posted journal lines
independently, so total debits exceeded credits by 46%. No finance function
would accept that. It was caught by `obs_reconciliation_controls`, which
evaluates double-entry as *data* rather than only as a test, and fixed by
emitting journals as balanced pairs.

The lesson I would take to a client: `not_null` and `unique` catch structural
faults. Business-plausibility and reconciliation controls catch the faults
that reach a board pack.

## 5. Decision support, not just reporting

`network_investment_scorecard` scores every site by combining trading
performance, growth, non-fuel mix, reliability, downtime, safety and asset
condition. Percentile ranks put rand figures and incident counts on a common
scale, and the weights are an explicit management judgement stated in the SQL
rather than a fitted parameter.

Every component is a visible column. A challenged recommendation can be
answered with its inputs rather than with "the model said so", which is the
only version of this that survives an executive forum.

Ranking is not allocation, so `ml/network_investment_engine.py` turns it into
a capital plan: an exact bounded knapsack over site/intervention pairs under
a fixed budget, with a minimum number of funded projects per province.

That constraint exists because a pure return-maximising plan concentrates
everything in Gauteng and the Western Cape. That is defensible financially and
indefensible as a network strategy — and the sole-coverage query in the SQL
set shows why: divestment candidates that are the only site within 50 km score
badly and should probably still be kept, because the volume does not transfer
to a competitor's neighbour 200 km away.

Result at portfolio scale:

| Recommendation | Sites | Avg score |
|---|---:|---:|
| Invest | 207 | 82.3 |
| Hold | 319 | 62.9 |
| Hold — strategic coverage | 281 | 37.8 |
| Review | 37 | 35.4 |
| Divest candidate | 206 | 16.7 |

## 6. Models that would survive production

Six MLflow experiments: demand forecast, predictive maintenance, customer
churn, stock-out risk, late delivery, and unsupervised forecourt anomaly
detection.

Three rules applied to all of them:

**Chronological splits, never random.** A random split on time-series data
leaks the future into training and produces an accuracy figure that will not
survive contact with production.

**No feature unknown at prediction time.** The stock-out model deliberately
excludes `days_of_cover`, even though the target is derived from it — the
model would score near-perfectly by reproducing the definition and be
worthless the moment the threshold changed. The late-delivery model uses only
pre-departure information. The maintenance model excludes cost and labour
hours, which are outcomes rather than predictors.

**A baseline that has to be beaten.** The demand forecast reports its error
against a seasonal-naive baseline — same weekday, last week — and prints a
warning if it fails to beat it. A model that cannot beat "last Tuesday" should
not be promoted, however good its R² looks.

The anomaly detection is unsupervised because there is no labelled fraud, and
in a real downstream business there rarely is. The run is tagged explicitly:
a high score means *unlike this site's own history*, not *fraudulent*. Most of
what surfaces will be a miscalibrated meter or a badly closed shift, and that
is still worth finding.

## 7. Governance designed to be restrictive by default

Unity Catalog column masks and row filters, mirrored by Power BI RLS so a user
sees the same rows whichever way they query.

The principle is that a new analyst sees masked customer names and no rows
outside their region until someone deliberately grants more. Getting this the
other way round is how platforms leak.

Two details worth calling out. Analysts get **no bronze access at all** — raw
data has no conformed definitions, and any number taken from it will disagree
with the dashboard. And the row-filter scope comes from a table rather than
from hard-coded group names, so adding a region to someone's remit is a data
change, not a deployment.

## 8. Engineering decisions

**Business definitions live in gold, not in DAX.** OTIF, stock-out risk and
margin percentage are computed once. A definition that lives in the BI layer
gets reimplemented by whoever builds the next report, and two dashboards
eventually disagree in front of an executive.

**The cleansing layer is split so the parsing is paid for once.** The first
version had `stg_` and `qtn_` each running the full repair-and-assess pipeline
over the same source, so every row was parsed twice and a single quarantine
model took 500 seconds. Splitting repair into a materialised stage that both
read from fixed it. Found by watching the clock, not by reasoning about it in
advance.

**The cleansing layer is generated, not hand-written.** 289 models derived
from the build manifest, which records each column's *intended* type — read
before defect injection, so the generator knows what a column is supposed to
be rather than guessing from damaged values. CI fails if the committed models
drift from what the generator produces.

**Partitioning by date was wrong, and the platform proved it.** Partitioning
the retail fact on `date_key` is the obvious choice — every query filters on a
date range. The maintenance job's own output showed the cost, on the same 5
million rows:

| Table | Layout | Files | Avg file size |
|---|---|---:|---:|
| `gold.fct_retail_fuel_sales` | partitioned by `date_key` | 974 | 0.2 MB |
| `gold.fct_retail_fuel_sales` | liquid clustered `(date_key, site_id)` | **2** | **94.4 MB** |
| `bronze.fact_retail_fuel_sales` | partitioned by `date_key` | 974 | 0.2 MB |
| `bronze.fact_retail_fuel_sales` | unpartitioned, compacted | **3** | **44.5 MB** |
| `bronze.fact_shop_sales` | partitioned by `date_key` | 974 | 0.1 MB |
| `bronze.fact_shop_sales` | unpartitioned, compacted | **1** | **48.9 MB** |

974 days in the window means 974 partitions of a fraction of a megabyte each.
`OPTIMIZE` never merges across a partition boundary, so those small files are
permanent, and every query pays 974 file-open costs to read a third of a
gigabyte. Liquid clustering gives the same data skipping without committing the
physical layout, and the keys can be re-chosen later without rewriting history.

A **487-fold** reduction in file count for identical data, found by reading the
maintenance job's own output rather than by reasoning about it in advance.

**A catalog per environment.** A dev job physically cannot write to prod
because the grant does not exist.

**Bronze is generated in-platform on Databricks.** Pushing 37 million rows
over a domestic connection takes hours; Spark produces the same distributions
on the cluster in minutes.

## 9. What I would do differently

**The row-count plan drove the model.** Starting from "we need 15 million
rows" produced 85 fact tables, some of which exist mainly to carry volume.
A real engagement would start from the decisions the business needs to make
and let the model follow. The bus matrix would be shorter and better for it.

**Uplift assumptions in the investment engine are asserted, not derived.**
"A convenience build lifts margin 22%" is a planning number I chose. In a real
engagement it would come from the sites that have already been converted —
which the data model can support, but which needs a before/after study rather
than an assumption.

**Anomaly detection has no feedback loop.** The model produces a worklist; a
production version would capture investigation outcomes and become supervised
within a couple of quarters. Without that it degrades into an alert nobody
opens.

**Streaming is demonstrated rather than operated.** The pipelines,
watermarks and windowing are real, but I have not run them under sustained
load or handled a poison message mid-stream. I would not claim production
streaming experience on the strength of this.

## 10. Reproducing it

```bash
pip install -r requirements.txt
PYTHONPATH=src python -m vivo360.build --profile portfolio \
  --output data/lake --defects realistic
cd dbt && dbt deps && dbt build
cd .. && pytest tests/ -v
```

About forty minutes on a laptop. `--profile dev` gives the same structure in
twenty seconds.
